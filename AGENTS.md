# Working on grafana-clickhouse-drilldown

This is a standalone Go application repository. No hosted Git remote has been
created, and no application implementation has been started. Do not create a
remote or choose a project license without authorization and dependency review.

## Plan and implementation

Read this project's OpenChamber implementation plan before building. It is
awaiting review. Show it to the user and wait for approval unless the user has
already approved or explicitly sent that plan for implementation. Tick its
coarse steps as they are completed; do not silently drop constraints.

Target the queries actually generated by Grafana Logs Drilldown. Do not promise
full Loki or LogQL compatibility. Parse the whole query, validate every stage,
and use one shared parameterized SQL compiler. Unsupported syntax must return
explicit errors rather than incorrect or successful empty results.

Review the pinned Loki parser's actual licenses, Go requirements, and dependency
cost before adopting it. Do not use Loki main or regex-based query extraction.

## Deployment boundaries

The planned new runtime directory is `/root/docker/clickhouse-loki-adapter` on
the existing `clickstack_internal` network, with a separate non-default Grafana
data source and a separate restricted ClickHouse reader. Keep queries bounded
for the 4 GiB host. Publish no LAN/VPN/public adapter ports. Production log
data must not be copied into disposable test Loki/ClickHouse instances.

The existing `clickstack` SQL data source remains Grafana's global default.
Leave `clickstack-prometheus`, its shared query queue, the SQL Logs Explorer,
and collectors unchanged.

The user authorizes removal of the old experimental adapter only once the
replacement passes the plan's core correctness and live acceptance gates.
Check consumers before removing data source UID `clickhouse-loki-test`.
Retire only that trial's containers, private HAProxy helper, and unused
`loki_adapter_test` reader/profile. Preserve narrowly scoped rollback material.
Never run broad prune, `down -v`, or broad recursive removal commands.

Update the infrastructure handbook's current operating notes when live
deployment or access changes. Distinguish tested behavior, known limitations,
and user confirmation. Never commit production log dumps or secrets.
